## ① 거래대금 단위 불일치 — 왜 이렇게 고쳤나

네이버 `itemSummary.naver`의 `amount` 필드 단위가 **시장별로 다르다**. 46종목 전수 검증
(`amount` vs `quant*now/1e6` 배율):

- 코스피 40종목 → 배율 ≈ 1 (백만원)
- 코스닥 6종목(알테오젠·에코프로비엠·주성엔지니어링·리노공업·이오테크닉스·제룡전기) → 배율 ≈ 1000 (천원)

정렬 시 코스닥이 1000배 부풀려져 상위 3을 영구 독식했다. 실제 21위(640억)·32위(339억) 종목이
"거래대금 상위"로 표시되고, 실제 1·2위 SK하이닉스(6.5조)·삼성전자(3.9조)는 **구조적으로 선정 불가**였다.
운영 규칙 0(화면의 모든 수치는 실측) 위반.

**선택한 해법**: `amount`를 신뢰하지 않고 `pollOne`이 이미 가져오는 `price * vol`로 직접 계산한다.
- 단위가 종목 불문 일관(원)이라 시장 구분 로직 자체가 불필요 — 코스닥/코스피 판별표를 들고 다니지 않아도 된다.
- 코스피 종목에서 `price*vol`이 `amount`와 2% 이내로 일치함을 확인(체결가 가중이 아닌 현재가 근사라 오차).
  순위 산정 목적에는 충분하고, 현 상태보다 압도적으로 정확하다.
- 부수 효과로 종목당 HTTP 호출 1회(46회)가 사라져 API가 빨라진다.

**ETF 경로는 건드리지 않는다.** ETF 16종목 전수 검증 결과 배율 0.96~1.04로 전부 백만원 단위 일관.
게다가 `etfBettingFlow`의 `downRatio` 테스트가 백만 스케일을 전제하고 있어, 바꾸면 테스트만 깨지고 이득이 없다.

## ② 상승장 카테고리 — 왜 필요한가

`counter_up`은 `sgn(pct) !== sgn(kospiPct)` **그리고** `pct - kospiPct >= 3.0`을 동시에 요구한다.
`kospiPct > 0`이면 앞 조건은 `pct <= 0`, 뒤 조건은 `pct >= kospiPct + 3 > 0` — **수학적으로 발화 불가능**.
상승장 전체에서 그렇다. 이건 설계 의도(역행 "상승"은 하락장 개념)라 그 자체는 버그가 아니지만,
**대응하는 반대편 카테고리가 없다는 게 공백**이다.

여기에 `vol_surge`는 `pct <= -3.0`을 요구하고, 수급 2종은 마감 후에만 계산됐다.
결과적으로 상승장 장중에 살아있는 카테고리는 `near_high`와 `turnover`뿐 → 관측된 3건과 정확히 일치.

신설:
- `counter_down`(역행 하락) — `counter_up`의 부호 대칭. 시장 상승분에 비례한 하한선(최대 1.5%)을 둬
  "살짝 빨강"인 종목이 전부 잡히는 것을 막는다. `counter_up`의 급락일 보정과 같은 사상.
- `surge_up`(거래량 급증 + 급등) — `vol_surge`의 부호 대칭. `pct >= +3.0`.

`vol_surge`의 META 라벨을 `거래량 급증` → `거래량 급증 · 급락`으로 바꿨다. 기존 라벨은 급락 조건을
숨기고 있어서 `surge_up` 추가 후엔 둘을 구분할 수 없다.

## ③ 장중 거래량 배수 — 분자·분모 축 불일치

`vol_avg20`은 `build_stocks_snapshot.py`가 일봉 `accumulatedTradingVolume` 20일 평균으로 만든다(**종일** 기준).
반면 `signals.mjs`의 `pollOne`은 폴링의 **당일 누적** 거래량을 쓴다. 서로 다른 축을 나눈다.

13:50은 정규장 390분 중 290분(74%) 경과 → 평균 수준 종목도 0.74x로 찍힌다. 실제 오늘 46종목 최대가
0.80x로 임계 1.5x에 아무도 근접하지 못했다. 오전 10시라면 진짜 1.5배 페이스 종목이 0.23x로 표시돼
사실상 발화 불가.

**해법**: 분모를 경과 비율로 축소(`vol_avg20 * progress`). 임계값 1.5는 그대로 두고 축만 맞춘다 —
새 신호를 발명하는 게 아니라 원래 의도대로 동작하게 만드는 교정이다.

`VOL_PROGRESS_FLOOR = 0.2`를 둔 이유: 개장 직후 `progress`가 0에 가까우면 분모가 0으로 수렴해 배수가
폭발한다. 하한을 두면 09:00~10:18 구간은 실제보다 **작은** 배수가 나와 보수적으로 동작한다
(오탐보다 미탐을 택함 — 운영 규칙 0의 "억지로 채우지 않는다"와 같은 방향).

코어는 순수 함수로 유지하기 위해 시계를 읽지 않고 `opts.progress`로 주입받는다. 기본값 1(=종일)이라
기존 호출부·테스트는 그대로 동작한다.

## ④ 장중 수급 — "잠정"이 아니라 "전일 기준"인 이유

당초 계획은 "장중에도 켜되 잠정 표기"였다. 그러나 실측 확인 결과
`m.stock.naver.com/api/stock/{code}/trend`는 **장중에 당일 행을 주지 않는다**
(2026-07-21 13:5x 조회 시 최신 행이 `bizdate 20260720` = 전일).

따라서 장중에 이 신호를 켜면 판정 근거는 "오늘의 잠정치"가 아니라 **어제 확정치**다.
"잠정"이라 표기하면 사실과 다르므로 배지 접미사를 ` (전일 기준)`으로 확정했다.
데이터는 실측 확정치이고 라벨도 정확해진다.

> 이 API가 나중에 장중 잠정 행을 주기 시작하면 접미사를 다시 검토할 것.
> **판단 근거는 "최신 행의 `bizdate`가 오늘인가"이지 시각이 아니다.**

## 테스트가 이 버그를 못 잡은 이유 (재발 방지)

`_signals-core.test.mjs` 22개는 전부 통과 중이었다. `amount`를 **이미 정규화된 값으로 주입**해
검증하기 때문이다. 버그는 순수 코어가 아니라 외부 데이터를 코어에 먹이는 **어댑터(`signals.mjs`)**에 있었다.

→ 외부 API 필드를 그대로 코어에 넘길 때는, 그 필드가 모든 입력에서 같은 단위·의미인지
   전수 검증하는 절차를 넣을 것. 순수 함수 테스트만으로는 어댑터 버그를 잡을 수 없다.
