# 컨텍스트 노트 — 홈 실적 캘린더 + 밸류에이션 상세 이전

작성 시작 2026-07-21. 결정과 그 근거를 이어서 적는다.

## 배경

코스피랩 대비 경쟁력 점검(`docs/reports/2026-07-21-kospilab-competitive-review.html`) 후속.
사용자가 홈의 **밸류에이션 시그널 블록을 제거**(커밋 966257cd)하고, 그 자리에 무엇을 넣을지 검토를 요청했다.

### 왜 밸류에이션을 뺐나 — 진단

제거 전 홈 메인 컬럼 구성이 이랬다.

| 블록 | 성격 |
| --- | --- |
| 🧭 섹터별 대표 종목 | 탐색 |
| ⚡ 특이 신호 | 발견 |
| 💰 밸류에이션 시그널 | 발견 |
| 📊 ETF 랭킹 | 탐색 |

**네 블록이 전부 "종목을 골라주는 랭킹"이었다.** 밸류에이션이 안 읽힌 건 기능 품질 문제가 아니라 같은 일을 하는 네 번째 목록이었기 때문으로 판단했다. 그래서 다섯 번째 랭킹을 넣지 않고 **없는 축(시간)** 을 채우기로 했다.

## 결정

## 데이터 소스 검증 (2026-07-21 실측)

### 실적 발표일 — 네이버 IR 채택, yfinance 기각

처음엔 `fetch_news.py`의 `_drop_stale_earnings`(커밋 bfcaee61)가 쓰는 yfinance `get_earnings_dates`를 재활용하려 했다. **두 가지 이유로 기각.**

1. **시간대 오차.** yfinance 인덱스는 `America/New_York` 기준이다. 삼성전자 2026-04-29 16:00 EDT를 KST로 바꾸면 **4월 30일 05:00**이 된다 — 날짜 그대로 쓰면 ±1일이 틀린다. 캘린더는 날짜가 전부인 기능이라 치명적이다.
2. **실제로 틀렸다.** yfinance는 삼성전자 2026-07-29·SK하이닉스 2026-07-28을 주는데, 네이버 IR은 각각 **07-30·07-29**다. 두 종목 다 하루씩 어긋난다.

채택한 소스는 `https://m.stock.naver.com/api/stock/{code}/integration` 의 `irScheduleInfo`.

```json
{"title":"2026년 2분기 경영실적 발표","irScheduleDate":"2026-07-30","irScheduleDday":9}
```

- **기업 IR 공시 기반**이라 한국 기업의 정본이다.
- **KST 네이티브** — 시간대 변환이 없으니 오차가 생길 여지가 없다.
- 제목이 같이 와서 "2분기 경영실적" 같은 맥락을 그대로 쓸 수 있다.
- `fetch_valuation.py`가 이미 쓰는 것과 같은 API 계열이라 새 의존성이 없다.

`irScheduleDday`는 **저장하지 않는다.** §20에서 두 번 사고 난 "상대 시간 라벨을 저장하면 안 된다" 규칙에 따라 D-day는 렌더 시점에 계산한다.

### 커버리지 실측

- **실적 일정: 24/46 종목** (2026-07-21 기준). 전부 7/23~7/31 구간 — 지금이 어닝시즌이라 밀도가 높다.
- 없는 22종목은 아직 IR 공시를 안 낸 것이다(보통 2~4주 전 공시). 시간이 지나면 자연히 채워지고 빠진다 — 캘린더는 "예정된 것"만 보여주면 되므로 결손이 아니다.
- **밸류에이션: 27/46 종목.** `valuation.json`이 코스피200 기반이라 KOSDAQ·비200 종목은 원천적으로 없다. 나머지 19종목은 섹션을 생략한다(운영규칙 0 — 억지로 채우지 않음).

> 검토 단계에서 "bfcaee61에 재활용 가능한 캘린더 코드가 있다"고 말했는데 **틀렸다.** 그건 캘린더 생성기가 아니라 미국 티커용 stale 실적 차단 게이트다. 기법만 참고했고 소스는 새로 정했다.

## 설계

### 실적 캘린더

- 신규 `scripts/fetch_earnings_calendar.py` — `stock_universe.json`의 46종목을 돌며 `irScheduleInfo` 수집
- 출력 `web/data/earnings-calendar.json` — `{updated_at, events:[{code,name,date,title}]}`
- **오늘(KST) 이후 일정만** 저장. 지난 일정은 캘린더가 아니다.
- 홈 블록은 `stocks-home.js`가 fetch → 날짜별 그룹 → D-day는 렌더 시 계산
- 일정이 0건이면 **블록 자체를 숨긴다** (빈 상태 표시 금지)
- `updated_at` 신선도 가드 — 오래됐으면 숨기고 콘솔 경고

### 밸류에이션 상세 이전

- `generate_html.py`에 `_valuation_for_code(code)` 신설 — `valuation.json`의 `undervalued`/`overvalued`에서 종목 탐색
- 데이터 없으면 `None` → 섹션 생략 (`_broker_targets_for_code`와 같은 패턴)
- `asOf` 신선도 가드도 목표주가와 같은 방식으로 건다

## 안 1 철회 — 실적 발표 캘린더 제거 (2026-07-21)

구현·검증까지 마치고 커밋했으나(58502ac7·3e386cc7), 사용자가 화면을 보고 "캘린더는 아닌 것 같다"고 판단해 철회했다. 데이터·기법 검증(네이버 IR 채택, yfinance 기각, 커버리지 24/46)은 사실로 남지만, **UI 판단은 실측만으로 확정되지 않는다** — 완성된 화면을 보고서야 어울리지 않는다는 게 드러났다.

- 제거 범위: `web/stocks/index.html`의 `#ern-block` 마크업, `stocks-home.js`의 `ernRender`/`ernDaysUntil`/`ernDday`/`ernDateLabel`/`loadEarnings` 등 전 함수 + 호출부, `stocks-home.css`의 `.ern-*` 규칙, `scripts/fetch_earnings_calendar.py`·`scripts/test_fetch_earnings_calendar.py`·`web/data/earnings-calendar.json` 삭제.
- 무엇이 왜 안 맞았는지는 사용자가 구체적으로 밝히지 않았다 — 다음에 "홈에 시간축을 채운다"는 방향으로 다시 시도할 때는 이 결과(캘린더 형태 자체가 기각됨)를 먼저 참고하고, 같은 형태를 반복 제안하지 않는다.
- 밸류에이션 상세 이전(안 3)은 이 철회와 무관하게 계속 진행한다.
