# 컨텍스트 노트 — 프리장 등락률 기준가 통합 (2026-07-30)

## 사용자 신고

홈 `/stocks` "밤사이 미국 반도체 시황"의 DRAM은 **-1.25%**인데, 클릭해서 들어간
`/stocks/us/dram/` 헤더는 **-7.35%**였다. 게다가 상세 페이지의 프리장 곡선은
저점 43.30 → 고점 44.26으로 **반등 중**이라, 한 화면 안에서 헤더와 곡선이
서로 다른 이야기를 하고 있었다.

## 조사 결과 — 곡선은 맞고 헤더 %만 틀렸다

가격은 두 화면이 사실상 같았다(44.29 vs 44.26, 폴링 시차). **분모만** 갈렸다.

| 화면 | API | 기준가 | 등락률 |
| --- | --- | --- | --- |
| 홈 | `/api/stocks-live` | 44.85 = 07-29 정규장 종가 | -1.23% ✅ |
| 상세 | `/api/intraday` | 47.77 = 07-**28** 종가 | -7.35% ❌ |

DRAM(Roundhill Memory ETF) 실제 일봉으로 확정했다.

```
07-27  52.43
07-28  47.77   ← 상세 페이지가 기준가로 쓴 값
07-29  44.85   ← 실제 직전 정규장 종가 (regularMarketTime = 07-29 16:00 ET)
```

07-29에 이미 -6.1% 빠진 것을 상세 페이지가 **오늘 프리장 낙폭으로 이중 계상**했다.
`(44.26 − 47.77) / 47.77 = −7.35%` — 화면 값과 정확히 일치해 산식까지 확인됐다.

홈은 5개 종목(DRAM·NVDA·MU·AVGO·SOXX)에서 전부 07-29 기준과 소수점까지 일치했다.
**홈은 처음부터 정상이었다.**

## 근본 원인 — Yahoo `previousClose`의 정의

`api/intraday.mjs:67`이 `meta.chartPreviousClose ?? meta.previousClose`를 기준가로 썼다.
그런데 이 필드는 **`regularMarketTime`(직전 정규장 마감) 기준 하루 전**이다.

- 정규장 중 → `regularMarketTime`이 오늘이므로 `previousClose` = 어제 종가 = **맞다**
- 프리장·애프터장 → `regularMarketTime`이 직전 마감이므로 `previousClose` = 그 **하루 전** = **틀리다**

즉 버그는 프리장·애프터장에만 나타난다 — 한국 사용자가 미국 종목을 보는 저녁·밤
시간대가 정확히 그 구간이다. DRAM·NVDA·AVGO·MU·SOXX 5종목 전부 동일하게 재현돼
**DRAM 고유 문제가 아니라 미국 상세 페이지 전체**의 구조적 오류로 확인됐다.

프리장 시점 meta 실측 (2026-07-30 04:51 ET).

```
regularMarketPrice = 44.85   ← 직전 완료 정규장 종가 (프리·애프터장의 올바른 기준가)
chartPreviousClose = 47.77   ← 그 하루 전
previousClose      = 47.77
```

## 왜 오래 안 들켰나 — §20 이중 소스

`api/stocks-live.mjs:81`은 프리·애프터장에서 `regClose`(= `regularMarketPrice`)를
기준가로 써서 **처음부터 정확했다**. 즉 정답 구현이 같은 저장소에 이미 있었는데,
두 API가 각자 기준가를 판정해서 한쪽만 맞았다.

SERVICE_RULES §20이 정확히 이 상황을 경고하고 있었다 — "같은 데이터를 두 화면에서
표시할 땐 같은 소스를 공유하게 만든다. 갈라져 있으면 한쪽만 고쳐지고 다른 쪽은
몇 주씩 방치돼도 겉보기엔 둘 다 정상 작동 중으로 보인다." 홈이 정상이었기 때문에
"프리장 등락률은 잘 나온다"는 인상이 생겨 상세 쪽 오류가 가려졌다.

## 설계 판단

### 기준가 판정을 서버에 두는 이유

`regularMarketPrice`의 **의미가 조회 시점에 따라 바뀐다** — 프리장엔 어제 종가,
애프터장엔 오늘 종가, 정규장엔 실시간 체결가다. 따라서 "어느 세션인가"의 판정과
meta 조회는 **같은 시점**이어야 한다. 클라이언트가 브라우저 시계로 세션을 정하고
서버가 30초 캐시된 meta를 주는 구조에서는 이 둘이 어긋날 수 있다.

그래서 서버가 세션을 판정하고 **기준가 자체(`baseClose`)를 내려준다**.
클라이언트는 고를 필요가 없다.

세션별 매핑 (네 경우 모두 클라이언트가 그리는 곡선 구간과 일치한다).

| 서버 판정 | 기준가 | 클라이언트가 그리는 구간 |
| --- | --- | --- |
| `pre` | `regularMarketPrice` (= 어제 정규장 종가) | 오늘 프리장 봉 |
| `open` | `chartPreviousClose` (= 어제 종가) | 오늘 정규장 봉 |
| `post` | `regularMarketPrice` (= 오늘 정규장 종가) | 오늘 애프터장 봉 |
| `closed` | `chartPreviousClose` | 직전 세션 정규장 봉 |

### stocks-live도 함께 건드리는 이유

최소 수정(intraday만)이 더 안전하지만, 그러면 판정 로직이 **두 곳에 남아** 이번과
같은 갈라짐이 다시 생긴다. 이번 버그의 근본 원인이 정확히 그것이므로
`api/_us-session.mjs`로 추출해 두 API가 공유하게 했다. 추출은 stocks-live의
**검증된 로직을 그대로** 옮긴 것이고, 테스트가 두 경로를 모두 커버한다.

파일명을 `_`로 시작한 이유는 Vercel이 `api/` 안의 `_` 접두 파일을 라우트로
만들지 않기 때문이다(기존 `_us-market-calendar.mjs` 등과 동일한 관례).

### `prevClose`를 남겨둔 이유

`/api/intraday`의 `prevClose`는 하위호환으로 유지한다. 국내 경로(`?code=`)
소비처가 여럿이고(`stocks-home.js`·`main.js`·`stock_sector.html`), 그쪽은
`prevClose`를 쓰지 않지만 응답 스키마를 좁히는 변경은 이 사고와 무관한 위험이다.
미국 상세만 `baseClose`를 우선 사용하고, 없으면 `prevClose`로 폴백한다.
