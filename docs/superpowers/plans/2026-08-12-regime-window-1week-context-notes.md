# 컨텍스트 노트 — 국면 판정 창 1주일 전환

## 왜 임계값을 같이 바꿔야 했나 (2026-08-12)

`WINDOW_DAYS`만 126→5로 바꾸면 기능이 조용히 죽는다. `COOL_THRESHOLD`/`HIGH_THRESHOLD`가
"창 전체 누적수익률의 정점 대비 %p"라서 창 길이에 비례하기 때문이다. 픽스처 측정에서 5일 창의
|cum| 중앙값은 1.80으로 126일 창(9.30)의 1/5 수준이고, 현재 상수(-15) 기준 cooled 발화율이
0.156 → **0.004**로 떨어졌다. 판정 자체는 예외 없이 돌아가므로 **테스트도 통과하고 페이지도
정상 렌더되는데 "교체" 카드만 영영 안 나오는** 형태로 실패한다 — SERVICE_RULES §20·§32가 경고한
"죽었는데 정상처럼 보이는" 실패 모드와 같은 계열이다.

## -2.5/-0.5를 고른 근거

백분위 매칭(-3.4/-0.4)이 통계적으로는 더 자연스러워 보였지만 채택하지 않았다. gap 분포를 맞추는
것과 **카드가 사용자에게 보여주는 상태 분포**를 맞추는 것은 다른 문제이고, 후자가 이 기능의
목적이다. 백분위 매칭은 swap 비율을 0.20(원본) → 0.08로 떨어뜨려 "주도주가 A에서 B로 넘어가는
중"이라는 핵심 서사를 대부분의 날에 없앤다.

-2.5/-0.5는 swap 0.25 · lead 0.62 · none 0.12로 원본(0.20 / 0.59 / 0.22)에 가장 가깝고,
국면 중앙 길이도 44일로 원본 51일과 비슷하다.

## MIN_RUN·HYST를 건드리지 않은 이유

`MIN_RUN`(10) · `HYST_WINDOW`(5) · `HYST_MIN`(3)은 **영업일 수** 단위다. 창 길이가 바뀌어도
"국면은 최소 10영업일 지속" · "최근 5일 중 3일 충족"이라는 의미가 그대로 성립한다. 그리드 탐색에서
MIN_RUN을 15·20으로 올려도 조건은 통과했지만, 요청 범위 밖의 변경이라 손대지 않았다(원본 리듬에
가장 가까운 것도 MIN_RUN=10이었다).

## 기존 회귀 가드가 그대로 통과한 것이 중요하다

`test_reproduces_observed_regimes`는 사용자가 실제로 관찰한 국면(5~6월 메모리 주도, 7월 이후 교체)을
박아둔 가드다. 창을 1/25로 줄였는데도 이 세 날짜의 판정이 동일하게 나왔다 — 임계값 재산출이
자의적이지 않았다는 독립적인 증거다. **이 테스트를 새 값에 맞춰 고쳐서 통과시키지 않았다는 점이
핵심이다.** 다음에 창을 또 바꾼다면 이 가드를 먼저 돌려보고, 실패하면 임계값 후보를 다시 잡을 것
(가드를 고치지 말 것).

## 스파크라인 샘플 간격을 유도값으로 바꾼 이유

기존 `cum[::-5]`는 "126일을 26점으로"라는 의도가 리터럴 `5`에 숨어 있었다. 창이 5일이 되면 이 식은
**2점**을 만들어 곡선이 직선이 된다 — 에러 없이 조용히. `WINDOW_DAYS`에서 stride를 유도해 같은
사고가 반복되지 않게 했다(126일에서는 stride가 그대로 5라 기존 출력이 바뀌지 않는다).

## 남은 트레이드오프 (사용자가 알고 선택함)

- 스파크라인 점이 26개 → 6개. 1주일에는 거래일이 5일뿐이라 일봉으로 그려도 6점이 상한이다.
- 바로 위 `#flow-block`(자금 지도)이 이미 `window_days: 5`다. 두 블록의 관측 기간이 같아졌다.
- "6개월 최고" 같은 라벨은 이제 `window_days`에서 유도한다 — 다음에 창을 바꿔도 라벨이 따로 놀지
  않는다(§20 "상대 라벨은 저장하지 말고 렌더 시점에 계산한다"와 같은 처방).
